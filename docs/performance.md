# Performance

This page records how the validator's speed and memory changed over three development rounds, and how it compares with [santhosh-tekuri/jsonschema](https://github.com/santhosh-tekuri/jsonschema) v6, a widely used Go validator for Draft 2020-12. The product's own benchmarks are described in [benchmarks.md](benchmarks.md).

## Versions

| Version | Commit | What it is |
|---|---|---|
| v1 | `09d8ec2` (tag `evaluation-candidate`) | Round 1: the feature-complete validator, 20 stories |
| v1.1 | `f35d9e4` (tag `performance-round-2`) | Round 2: 7 performance stories |
| v1.2 | tag `v1.2.0` | Round 3: 7 more performance stories, plus the module-path rename |

All three passed the same 1,302 / 1,302 required tests of the official JSON Schema Test Suite and fail the same optional cases (see the README's Conformance section). v1.2's CLI output is byte-identical to v1.1's in all four output formats.

### Peak memory of the CLI

Peak resident memory of the `jsonschema` process validating the 5.5 MB document with `-o basic`, as measured by `/usr/bin/time -l`:

| v1 | v1.1 | v1.2 |
|---|---|---|
| 315 MiB | 198 MiB | 149 MiB |

The memory still held after decoding a 5.5 MB document (about 52 MiB) is unchanged since v1.1. The decoded-document representation has not been reworked yet.

## What changed

**Round 2 (v1.1)** made the evaluation lazy where nothing observes it:
- Keyword locations are built only when they're reported.
- The evaluated-property record is kept only when an `unevaluated*` keyword can see it.
- Annotations are kept only when they can be observed.
- The meta-schema set is built once per process.
- Numbers are stored compactly, with an `int64` fast path.

**Round 3 (v1.2)** removed per-node bookkeeping:
- Evaluation path frames are reused per depth, with no closure on node entry.
- One child evaluation context is kept per depth.
- Object keywords sort member names on the stack, without copies.
- Annotations are collected in growing chunks and flattened only when read.
- The report is rendered with a size hint and without per-segment string copies.
- `multipleOf` uses integer arithmetic on the common path.
- The built-in meta-schema index is built once instead of twice.

None of these changes alters validation results, output, exit codes, limits or goroutine safety. Each was checked with `go test -race` and a byte-for-byte comparison of the CLI's output.

## Method and caveats

- **Environment:** Apple M3 Max (16 cores), macOS, Go 1.27.2.
- **Workload:**
  - One schema (an order with nested items, using `$ref`, `pattern`, `multipleOf`, `uniqueItems` and `additionalProperties`; see `testdata/perf/order_schema.json`).
  - Documents generated by the product's own fixture recipe (`internal/perfdata`): 10, 10,000 and 100,000 items, plus a 10,000-item document in which every tenth item is invalid.
  - Other schema shapes may rank differently.
- **Fairness:**
  - Both validators read identical bytes, and timing includes JSON parsing for both.
  - tekuri runs with its default compiler.
  - Before timing, a test checks that both give the same verdict on every document.
  - Rendering an error report is not part of the head-to-head.
- **Memory:** "bytes allocated" is the total allocated per operation (`-benchmem`). It is not peak or retained memory.
- **Reproducibility:**
  - The comparison harness lives outside this repository, so that no other validator ever becomes a dependency here.
  - It is a short Go benchmark file that imports both modules and uses the same document recipe; it is available on request.
  - The product's own benchmarks, without tekuri, run with `go test -run '^$' -bench . -benchmem .`.
